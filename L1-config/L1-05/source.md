# L1-05 · AutoModel 分派：字符串如何找到类 — 源文件

**这一课只回答一个问题：`config.json` 里的一个字符串，是怎么变成一个可以实例化的类的？**

视角：第 1 层说"config 决定形状"。但在形状被决定之前，先得有人**找到**那个 config 类 ——
这条从字符串到类的路，全程是几张**纯字符串表**加两次 `importlib.import_module`。

| 文件 | 行数 | 本课引用块 |
|---|---|---|
| `models/auto/__init__.py` | 34 | 2 |
| `models/auto/configuration_auto.py` | 466 | 5 |
| `models/auto/auto_factory.py` | 707 | 4 |
| `models/auto/auto_mappings.py` | 1359 | 2 |

> 行数取自 `_data/universe.json`（比 `wc -l` 各多 1：这几个文件的末行都没有换行符）。

**实测环境**（`_data/recon/probe_l105.py`，transformers 5.18.0.dev0，CPU 机器）：

```text
import transformers 之后              transformers.* 模块 240 个；glm5_next.configuration 未加载
刚 import auto_mappings 时             CONFIG_MAPPING_NAMES 718 条，值全是 str
导入 configuration_auto 之后           同一张表 723 条（就地 update +5）；CONFIG_MAPPING.keys() 724（+gpt-sw3）
len(AutoModel._model_mapping)        556，新增 0 个模块，0.1 ms
CONFIG_MAPPING.keys()                724 项，新增 0 个模块，0.2 ms
CONFIG_MAPPING['glm5_next']（冷）      新增 2 个模块，6.8 ms
AutoModel._model_mapping[Glm5NextConfig]  新增 101 个模块，172.4 ms
CONFIG_MAPPING.values()（全都要）       新增 1000 个模块，1553 ms；总数 1415
AutoConfig.for_model('glm5_next')    Glm5NextConfig；text_config.hidden_size = 4096，45 层
```

> 上面这段是**实测输出**，用 `text` 块标出 —— 它不是源文件的逐字引用，因此不参与保真校验。
> 下面每一段 `python` 块都是逐字引用，且每一块前面都有一行 `<!-- src: ... -->`。

## 一、最外层：`models/auto/__init__.py` 连自己都是惰性的

先看这个包的入口。它短到可以整段读完，却把"惰性"这件事做到了包一级：
**`import transformers.models.auto` 本身不会导入 auto 下面的任何一张表。**

<!-- src: models/auto/__init__.py -->
```python
if TYPE_CHECKING:
    from .auto_factory import *
    from .configuration_auto import *
    from .feature_extraction_auto import *
    from .image_processing_auto import *
    from .modeling_auto import *
    from .processing_auto import *
    from .tokenization_auto import *
    from .video_processing_auto import *
```

**读法**：
- 这 8 行 star-import 在**运行时一次都不会执行**。`TYPE_CHECKING` 在解释器里恒为 `False`，
  只有 mypy / pyright 这类类型检查器才当它 `True`。
- 所以这 8 行是**给人和工具看的声明**，不是代码路径。真正决定这个包导出什么的是下面的 `else`。

<!-- src: models/auto/__init__.py -->
```python
else:
    import sys

    _file = globals()["__file__"]
    sys.modules[__name__] = _LazyModule(__name__, _file, define_import_structure(_file), module_spec=__spec__)
```

**读法**：
- `sys.modules[__name__] = _LazyModule(...)` 是整段的关键：它把**解释器缓存里的这个模块对象整个换掉**。
  之后任何 `from transformers.models.auto import AutoConfig`，拿到的都是这个 `_LazyModule`，
  由它按 `define_import_structure(_file)` 扫出来的结构决定某个名字要不要真的去 import。
- `_file = globals()["__file__"]` 之所以要绕一下，是因为这个模块对象马上要被替换掉，
  后面不能再依赖 `__file__` 这个名字的常规绑定。
- 这一层惰性不是免费的：`_LazyModule` 要在第一次属性访问时补一次 import。
  但收益是 **`import transformers` 完全不必碰 500 多个模型子包**（`models/` 下有 521 个子目录）——
  实测：`import transformers` 之后有 240 个 `transformers.*` 模块，没有一个属于 `glm5_next`。

## 二、第一跳：`"glm5_next"` → `"Glm5NextConfig"`（表里全是字符串）

分派链的第一跳发生在一张纯数据表里。`models/auto/auto_mappings.py` 是**自动生成**的，
文件头第 2 行原话是 `Do NOT edit this file manually`（要改就改 config 类的 `model_type`，
然后跑代码生成器重写整张表）。它的正文只有一张表：

<!-- src: models/auto/auto_mappings.py -->
```python
        ("glm5_next", "Glm5NextConfig"),
        ("glm5_next_text", "Glm5NextTextConfig"),
        ("glm5_next_vision", "Glm5NextVisionConfig"),
```

**读法**：
- 右边是 `"Glm5NextConfig"` —— 一个**字符串**，不是类。这一点决定了后面必须有人去 `import` 并 `getattr`。
- 实测：这张表一共 **718 条**，键和值的类型都是 `str`。读这张表
  （`from ...auto_mappings import CONFIG_MAPPING_NAMES`）**不会**导入任何模型包。
- `Glm5NextConfig` / `Glm5NextTextConfig` / `Glm5NextVisionConfig` 三条并列，
  说明它们是三个各自独立的 `model_type`：顶层复合配置、文本子配置、视觉子配置各占一个名字。

还有一张反向的小表。`model_type` 里的 `-` 与多配置共包的情况，都靠它归一：

<!-- src: models/auto/auto_mappings.py -->
```python
        ("glm5_next_text", "glm5_next"),
        ("glm5_next_vision", "glm5_next"),
```

**读法**：
- `SPECIAL_MODEL_TYPE_TO_MODULE_NAME` 只在两种情况下需要登记：名字里有连字符、
  或者"一个包里住着多个 `model_type`"。`glm5_next_text` / `glm5_next_vision` 属于后者 ——
  它们和 `glm5_next` 是同一个包，所以在这里被指回去。
- 注意 `glm5_next` 自己**没有**出现在这张表里：它的名字本身就是合法包名，走默认那条路（见第四节）。

## 三、★ 表里没有一个类：`_mapping` 是字符串，`_extra_content` 才是对象

★ 这是本课第一个真正的洞察。上面那张表是机器生成的，但总有不按命名规则来的模型，
于是 `configuration_auto.py` 在导入时**就地**把它改大：

<!-- src: models/auto/configuration_auto.py -->
```python
CONFIG_MAPPING_NAMES.update(
    {
        "EvollaModel": "EvollaConfig",
        "mlcd": "MLCDVisionConfig",
        "parakeet_tdt": "ParakeetTDTConfig",
        "vibevoice_acoustic_tokenizer_decoder": "VibeVoiceAcousticTokenizerDecoderConfig",
        "vibevoice_acoustic_tokenizer_encoder": "VibeVoiceAcousticTokenizerEncoderConfig",
    }
)
```

**读法**：
- ★ 这段代码的位置说明了一件事：**表是可以被就地修改的**。注释写得很直白：
  `New models should follow consistent naming instead of being added here!` ——
  这 5 条是例外，不是模板。实测这条链的三个数字，正好把这段代码的行为量出来了：

  ```text
  刚 import auto_mappings 时   CONFIG_MAPPING_NAMES = 718 条（自动生成的原始表）
  执行完上面这个 update 之后    同一张表 = 723 条（+5，就地修改，不是新对象）
  再执行第 48 行的 gpt-sw3 包装   CONFIG_MAPPING.keys() = 724 条（这一行生成了新的 OrderedDict）
  ```

  718 → 723 → 724 这三个数不是笔误：**前两步改的是同一个对象，第三步换了一个对象**。
- ★ 另有一条路是给**用户**准备的（不在本课引用范围内，见 `AutoConfig.register`）：
  它写进的是 `_extra_content`，而 `_extra_content` 里存的是**真正的类对象**。
  所以这张注册表内部其实有两种东西：`_mapping`（字符串，懒）和 `_extra_content`（类对象，急）。
  后面 `__getitem__` 的第一行先查 `_extra_content`，就是因为那批是"已经拿在手上"的。
- 跨课呼应：**L1-01** 讲的是 `PreTrainedConfig` 的公共契约。
  这条链只负责"找到类"，不负责"校验类" —— 交付出去的对象要满足那份契约，是下一课的事。

## 四、第二跳：类名 → 模块名（`-` 换成 `_`，特例改名）

拿到类名之后，得先知道去哪个包里找。这个转换就是 `model_type_to_module_name`：

<!-- src: models/auto/configuration_auto.py -->
```python
def model_type_to_module_name(key) -> str:
    """Converts a config key to the corresponding module."""
    # Special treatment
    if key in SPECIAL_MODEL_TYPE_TO_MODULE_NAME:
        key = SPECIAL_MODEL_TYPE_TO_MODULE_NAME[key]

        if key in DEPRECATED_MODELS:
            key = f"deprecated.{key}"
        return key

    key = key.replace("-", "_")
    if key in DEPRECATED_MODELS:
        key = f"deprecated.{key}"

    return key
```

**读法**：
- `key.replace("-", "_")` 是硬需求：表里存在 `transfo-xl`、`bert-generation` 这种带连字符的
  `model_type`，而 Python 的模块名不能有 `-`。实测：`transfo-xl` → `transfo_xl`、
  `bert-generation` → `bert_generation`、`audio-spectrogram-transformer` → `audio_spectrogram_transformer`。
- 而 `glm5_next`、`glm5_next_text`、`glm5_next_vision` **三者都归一成 `glm5_next`** ——
  这就是第二节那张小表的用处：三个 `model_type`，一个包。
- 最后那个 `if key in DEPRECATED_MODELS` 分支现在**是死代码**：同一文件的第 61 行是
  `DEPRECATED_MODELS = []`（实测打印出来就是空列表）。留着是为了将来真要下线某个模型时不用改这里。
  这正是 STYLE 提醒的那类情况：**分支和注释不一定是活的**，要回文件里核对常量本身。

## 五、★ 「用时才导入」就发生在这 4 行里

`CONFIG_MAPPING` 是一个 `_LazyConfigMapping` 实例。前面所有的字符串铺垫，都是为了这 16 行里的 4 行：

<!-- src: models/auto/configuration_auto.py -->
```python
    def __getitem__(self, key: str) -> type[PreTrainedConfig]:
        if key in self._extra_content:
            return self._extra_content[key]
        if key not in self._mapping:
            raise KeyError(key)
        value = self._mapping[key]
        module_name = model_type_to_module_name(key)
        if module_name not in self._modules:
            self._modules[module_name] = importlib.import_module(f".{module_name}", "transformers.models")
        if hasattr(self._modules[module_name], value):
            return getattr(self._modules[module_name], value)

        # Some of the mappings have entries model_type -> config of another model type. In that case we try to grab the
        # object at the top level.
        transformers_module = importlib.import_module("transformers")
        return getattr(transformers_module, value)
```

**读法**：
- ★ 第 109–111 行是本课的主角：`model_type_to_module_name(key)` 算出包名 →
  `importlib.import_module(f".{module_name}", "transformers.models")` 拉包 →
  `hasattr` / `getattr` 把类取出来。**整个惰性分派只有这一处真正碰 import 系统。**
- `self._modules` 是**包级缓存**：`glm5_next_text` 和 `glm5_next_vision` 算出来的 `module_name`
  都是 `glm5_next`，所以第二次访问直接命中缓存，连 `importlib.import_module` 都不用调
  （就算调了也会被 `sys.modules` 兜住，但缓存让这一步连函数调用都省了）。
- 第 115–118 行的兜底很说明问题：`hasattr` 不成立时，转为 `import transformers` 再 `getattr`。
  有些表的条目指向**别的模型的类**，而那个类可能已经被提到 `transformers` 顶层导出了 ——
  这是"表由代码生成"留下的历史包袱。
- ★ 对比同一个类里另外几个方法，惰性的边界就清楚了：`keys()` / `__iter__()` / `__contains__()`
  只读 `self._mapping` 的键，**一行都不导入**；而 `values()` / `items()` 要真的把类拿出来，
  所以会**把 700 多条全部导入**。实测：`keys()` 新增 0 个模块、0.2 ms；
  `values()` 新增 1000 个模块、1553 ms。
  同一个对象，一个方法免费、一个方法昂贵 —— 这就是"惰性"的准确含义：
  **它不消除成本，只推迟成本。**

## 六、入口函数：`from_pretrained` 里的字符串从哪来

链路清楚了，回头看调用方。`AutoConfig.from_pretrained` 里决定分派的那 7 行：

<!-- src: models/auto/configuration_auto.py -->
```python
        config_dict, unused_kwargs = PreTrainedConfig.get_config_dict(pretrained_model_name_or_path, **kwargs)
        has_remote_code = "auto_map" in config_dict and "AutoConfig" in config_dict["auto_map"]
        has_local_code = "model_type" in config_dict and config_dict["model_type"] in CONFIG_MAPPING
        explicit_local_code = has_local_code and not CONFIG_MAPPING[config_dict["model_type"]].__module__.startswith(
            "transformers."
        )
        if has_remote_code:
```

**读法**：
- 第 397 行 `PreTrainedConfig.get_config_dict(...)` 把 `config.json` 读成一个**普通字典**。
  分派用的字符串就在这个字典里 —— 它不是函数参数。
- 第 399 行的 `in CONFIG_MAPPING` 走的是 `_LazyConfigMapping.__contains__`：
  只查 `_mapping` 和 `_extra_content` 的键，**不触发任何 import**。
- 第 400–402 行的 `explicit_local_code` 却会真的去取类（`CONFIG_MAPPING[...]`）并看它的 `__module__`
  是否以 `"transformers."` 开头 —— 用来区分"原生实现"和"某个包自己注册的同名实现"。
  **同一个函数里，相隔两行，一次不导入、一次导入。**
- 于是那句常见写法 `AutoConfig.from_pretrained('glm5_next')` 需要修正一下：
  第一个参数是**仓库 id 或本地路径**（源码 docstring 写的是 "A string, the *model id* of a
  pretrained model configuration hosted inside a model repo"），而 `"glm5_next"` 是 `model_type`
  的取值，不是仓库名。想直接按 `model_type` 造配置，用 `AutoConfig.for_model("glm5_next")`
  （实测返回 `Glm5NextConfig`，`text_config.hidden_size = 4096`、45 层）。
  **把两者混起来，是这一课最常见的误解。**

真正拿到类、准备实例化的那一段在函数末尾：

<!-- src: models/auto/configuration_auto.py -->
```python
        elif "model_type" in config_dict:
            # Apply heuristic: if model_type is mistral but layer_types is present, treat as ministral
            if config_dict["model_type"] == "mistral" and "layer_types" in config_dict:
                logger.info(
                    "Detected mistral model with layer_types, treating as ministral for alternating attention compatibility. "
                )
                config_dict["model_type"] = "ministral"

            try:
                config_class = CONFIG_MAPPING[config_dict["model_type"]]
```

**读法**：
- `CONFIG_MAPPING[config_dict["model_type"]]` 就是第五节那 16 行。`except KeyError` 对应
  `__getitem__` 里的 `if key not in self._mapping: raise KeyError(key)` ——
  **不认识的 architecture 在这里被翻译成一句人话**，而不是一个裸的 `KeyError`。
- 顺带一个真实的特例：第 420–425 行的启发式会在 `model_type == "mistral"` 且配置里有 `layer_types` 时
  **把字符串改写成 `"ministral"`**。字符串在分派之前是可以被改写的 ——
  这条规则本身就说明 `model_type` 是运行时数据，不是编译期常量。
- 最后一步是 `config_class.from_dict(config_dict, **unused_kwargs)`：
  类找到之后，**建实例的活交给类自己**（`from_dict` 属于 L1-01 讲的公共契约）。

## 七、★ 同一套手法用了第二次：config 类 → 模型类

★ 第二个洞察在这里：`AutoModel.from_pretrained(...)` 拿到 `config` 对象后还要再选一次类，
而这次的键是 **config 类本身**，不是字符串：

<!-- src: models/auto/auto_factory.py -->
```python
class _LazyAutoMapping(OrderedDict[type[PreTrainedConfig], _LazyAutoMappingValue]):
    """
    A mapping config to object (model or tokenizer for instance) that will load keys and values when it is accessed.

    Args:
        - config_mapping: The map model type to config class
        - model_mapping: The map model type to model (or tokenizer) class
    """

    def __init__(self, config_mapping, model_mapping) -> None:
        self._config_mapping = config_mapping
        self._reverse_config_mapping = {v: k for k, v in config_mapping.items()}
        self._model_mapping = model_mapping
        self._model_mapping._model_mapping = self
        self._extra_content = {}
        self._modules = {}
```

**读法**：
- ★ `_LazyAutoMapping` 的构造函数里最重要的是第 593 行：
  `self._reverse_config_mapping = {v: k for k, v in config_mapping.items()}`。
  它把 `{model_type: "Glm5NextConfig"}` 反过来变成 `{"Glm5NextConfig": model_type}` ——
  **键又回到了字符串**，于是后面可以复用第二节那套"按 `model_type` 找包"的手法。
- 第 595 行 `self._model_mapping._model_mapping = self` 是一条**反向引用**：把映射对象自己挂回名字表。
  `auto_class_update` 生成 `from_pretrained` 的 docstring 时
  （`replace_list_option_in_docstrings(model_mapping._model_mapping, ...)`）要用它。
  裸的 `OrderedDict` 上可以随便挂属性，这是 Python 的便利，也是这里唯一的"隐式契约"。
- `__init__` 里**没有 import**。真正导入在下面这两个方法里：

<!-- src: models/auto/auto_factory.py -->
```python
    def __getitem__(self, key: type[PreTrainedConfig]) -> _LazyAutoMappingValue:
        if key in self._extra_content:
            return self._extra_content[key]
        model_type = self._reverse_config_mapping[key.__name__]
        if model_type in self._model_mapping:
            model_name = self._model_mapping[model_type]
            return self._load_attr_from_module(model_type, model_name)

        # Maybe there was several model types associated with this config.
        model_types = [k for k, v in self._config_mapping.items() if v == key.__name__]
        for mtype in model_types:
            if mtype in self._model_mapping:
                model_name = self._model_mapping[mtype]
                return self._load_attr_from_module(mtype, model_name)
        raise KeyError(key)
```

<!-- src: models/auto/auto_factory.py -->
```python
    def _load_attr_from_module(self, model_type, attr):
        module_name = model_type_to_module_name(model_type)
        if module_name not in self._modules:
            self._modules[module_name] = importlib.import_module(f".{module_name}", "transformers.models")
        return getattribute_from_module(self._modules[module_name], attr)
```

**读法**：
- `_load_attr_from_module` 和 `_LazyConfigMapping.__getitem__` 是**同一个套路**：
  算模块名 → `importlib.import_module(f".{module_name}", "transformers.models")` → 取属性。
  第 621–622 行甚至把 `self._modules` 缓存也照抄了一份。
  **同一个仓库里两处独立实现同一套惰性分派** —— 因为它们分属两个类，没有公共基类。
- `__getitem__` 的查找顺序值得记：先查 `_extra_content`（用户 register 进来的），
  再用 `key.__name__` 反查 `model_type` 走正常路，最后才退化成"线性扫描所有指向同一 config 的
  model_type"。一个 config 类对应多个 `model_type` 时，靠的就是最后这个 `for` 循环。
- 实测：`AutoModel._model_mapping[Glm5NextConfig]` 返回的是
  `<class 'transformers.models.glm5_next.modeling_glm5_next.Glm5NextModel'>`，**不是 tuple**
  —— 因为 `Glm5NextConfig` 只对应一个 `model_type`。多候选时才是 tuple。
- 拿到候选之后还有最后一步筛选，按 `config.architectures` 挑：

<!-- src: models/auto/auto_factory.py -->
```python
def _get_model_class(config, model_mapping):
    supported_models = model_mapping[type(config)]
    if not isinstance(supported_models, (list, tuple)):
        return supported_models

    name_to_model = {model.__name__: model for model in supported_models}
    architectures = getattr(config, "architectures", [])
    for arch in architectures:
        if arch in name_to_model:
            return name_to_model[arch]

    # If not architecture is set in the config or match the supported models, the first element of the tuple is the
    # defaults.
    return supported_models[0]
```

**读法**：
- `config.architectures` 是 `config.json` 里的一个字段（值是类名列表）。
  多候选时按它匹配；匹配不上就退回 `supported_models[0]` ——
  注释写得很清楚：第一个元素就是默认值。
- 到这一步，"字符串 → 类"的整条路才算走完：
  `model_type` 选 config 类，config 类选模型类，`architectures` 在多候选里做最后一次裁决。

## 八、惰性映射省下了什么（实测）

把"点名一个"和"全都要"放在同一次冷启动里量，惰性的账才算得清：

```text
操作                                      新增 transformers.* 模块    耗时
import transformers                      —                         —
+ 拿到 AutoConfig / AutoModel              72（240 → 312）           —
len(AutoModel._model_mapping) = 556       0                        0.1 ms
CONFIG_MAPPING.keys() = 724 项             0                        0.2 ms
CONFIG_MAPPING['glm5_next']               2                        6.8 ms
AutoModel._model_mapping[Glm5NextConfig]  101                      172.4 ms
CONFIG_MAPPING.values() = 724 项（全都要）   1000                     1553 ms
—— 全量遍历之后，transformers.* 模块总数 1415
```

**读法**：
- 省下的不是"一次 import"，而是**把 500 多个模型包的导入成本，从"任何一次 `import transformers`"
  推迟到"用户真的点名某个 `model_type`"**。只服务一个模型时，那 1000 个模块、1.5 秒永远不用付。
- 注意哪几次是**真的免费**：`len()` 和 `keys()` 新增 0 个模块。它们只对表做集合运算和键遍历，
  一个类都没取出来 —— 这就是"表里存字符串"换来的好处。
- 反过来，惰性映射**不省**"全都要"的钱：`values()` / `items()` / 自动生成 docstring
  都是全量遍历，一样得把 700 多条全部导入。用之前要清楚自己调的是哪一类。
- 首次取模型类那 101 个模块、172 ms 是**这个包的真实体积**（`modeling_glm5_next.py` 有 2444 行，
  见 L0-01）；config 那边只花 2 个模块、6.8 ms。同一次分派的两跳：按模块数差 50 倍（101 : 2），
  按时间差 25 倍（172 ms : 6.8 ms）。

```text
  config.json:  {"model_type": "glm5_next", "architectures": ["Glm5NextForConditionalGeneration"], ...}
        │
        │ ① PreTrainedConfig.get_config_dict()                 —— 读文件，得到一个普通 dict
        ▼
  config_dict["model_type"] = "glm5_next"                        ← 全链路唯一的字符串来源
        │

        ▼
  "Glm5NextConfig"                                              （类名，仍是字符串）
        │
        │ ③ model_type_to_module_name("glm5_next")             —— 纯字符串替换，零导入

        │

        ▼
  <class Glm5NextConfig>                                        （终于是类了）
        │
        │ ⑤ config_class.from_dict(config_dict, **unused_kwargs)
        ▼
  Glm5NextConfig 实例                                            （交给 L1-01 的契约）
```

**一句话总结**：

> 分派链上没有任何一个"注册表里的类"：表里存的是 `str → str`，类只在被点名的那一刻，
> 由一处 `importlib.import_module` + `getattr` 从包里取出来。
> **惰性映射不消除导入成本，只把它从 `import transformers` 推迟到第一次点名。**
